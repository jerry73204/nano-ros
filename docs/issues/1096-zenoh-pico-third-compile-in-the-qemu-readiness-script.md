# One vendored tree, THREE compilers

phase-420 W9 landed `packages/rmw/zenoh/zpico-sys/zenoh-sources.txt` on the
premise, stated in its own header and in `check-zenoh-source-manifest`'s
docstring, that the vendored zenoh-pico C is compiled **twice**: by
`nros-zpico-build` for the cargo lane and by `zephyr/cmake/nros_rmw_zenoh.cmake`
for the west lane. Measured 2026-09-05 while answering W9's "can one image hold
TUs from both lanes" question: **it is compiled three times.**

The third is `scripts/qemu/build-zenoh-pico.sh`, which cross-compiles the tree
for Cortex-M3 (`build/qemu-zenoh-pico/libzenohpico.a`). It is live — `just qemu
build-zenoh-pico` is invoked from `build-all.mk:79` and
`just/qemu-baremetal.just:460` — and it carries its own copy of FOUR things the
rest of the tree derives.

**The strongest evidence that the drift is real is that the file announces every
one of them.** Four comments, quoted verbatim with their line numbers, each
saying out loud that it is a restatement of something computed elsewhere:

```
 56: # Generate version header (matches build.rs generate_embedded_version_header)
 79: # Generate config header (matches build.rs generate_config_header)
 85:  * Matches the config header generated by zpico-sys/build.rs for bare-metal.
193: # Platform defines (matches build.rs build_zenoh_pico_embedded)
208: # Shim slot counts (matches ShimConfig defaults in build.rs)
```

A "matches X" comment is a mirror with the drift-detector left out; it is the
shape of every duplication this area has already paid for (issue 1068 next door,
the sizes-header mirror family 0088→0268, the pre-W9 nine-globs-twice). What
each covers:

1. **The source selection**, lines 153-164 — the one thing NOT announced by a
   "matches" comment, which is why nothing pointed at it:

   ```sh
   153: # Collect zenoh-pico source files (excluding platform-specific system backends)
   155: for dir in api collections link net protocol session transport utils; do
   156:     for f in $(find "$ZENOH_PICO_DIR/src/$dir" -name "*.c" 2>/dev/null); do
   ...
   162: for f in $(find "$ZENOH_PICO_DIR/src/system/common" -name "*.c" 2>/dev/null); do
   ```

   Those eight directories plus `system/common` are exactly the nine `dir`
   records in `zenoh-sources.txt`, written a third time.
   `check-zenoh-source-manifest`'s check (4) — "NEITHER LANE NAMES A PATH INSIDE
   THE VENDORED TREE" — is true of the two lanes it knows about and false of the
   repository: this script names nine.

2. **The generated config header**, the heredoc at lines 80-151, whose own body
   says at line 85 *"Matches the config header generated by zpico-sys/build.rs
   for bare-metal"* and at 86 *"DO NOT EDIT — regenerated on every build"* — of a
   file that is not regenerated by anything, only re-typed. ~40 `Z_FEATURE_*`
   values restated beside the ones `generate_config_header` computes, including
   `Z_FRAG_MAX_SIZE 1500` / `Z_BATCH_UNICAST_SIZE 2048`, which the cargo lane
   derives per platform through `ZenohBufferConfig` and the RFC-0049 ladder.

3. **The platform defines**, lines 193-206 (*"matches build.rs
   build_zenoh_pico_embedded"*) — `ZENOH_GENERIC`, `ZPICO_SMOLTCP`, ten
   `Z_FEATURE_*` overrides and `ZENOH_DEBUG=0`, restated a second time inside
   the same script after the header above already stated most of them.

4. **The shim slot defaults**, lines 208-215 (*"matches ShimConfig defaults in
   build.rs"*):

   ```sh
   DEFINES="$DEFINES -DZPICO_MAX_PUBLISHERS=8"
   DEFINES="$DEFINES -DZPICO_MAX_SUBSCRIBERS=8"
   DEFINES="$DEFINES -DZPICO_MAX_QUERYABLES=8"
   DEFINES="$DEFINES -DZPICO_MAX_LIVELINESS=16"
   DEFINES="$DEFINES -DZPICO_MAX_PENDING_GETS=4"
   DEFINES="$DEFINES -DZPICO_GET_REPLY_BUF_SIZE=4096"
   DEFINES="$DEFINES -DZPICO_GET_POLL_INTERVAL_MS=10"
   ```

   Seven literals, none read from the knob ladder that owns them — the same
   ladder (`nros_resolve_knobs()` → `NROS_RESOLVED_*`, `KCONFIG_KNOBS` →
   `$DOTCONFIG`) that issues 0460 and 0626 exist to keep single-valued, and that
   `check-kconfig-knob-forwarding` holds the two real lanes to. This script is
   outside that gate's reach.

## Why it is `low` and not `medium`

The artifact is **not linked into any image**. The script's own header says so:
*"This produces a standalone .a that serves as a build-readiness check for QEMU
E2E tests. The actual linking is done by zpico-sys/build.rs via cc::Build."* So
the failure mode is not a wrong image — it is a **false green readiness check**:
after an upstream rebase adds a directory, or after a knob default moves, this
script keeps compiling yesterday's set with yesterday's values and reports the
bare-metal build as healthy. It answers a question about a build nobody
performs.

That is also why it is worth fixing rather than deleting outright without
thought: a readiness check that has silently stopped tracking the build it
proxies for is worse than no check, and "delete it" is a legitimate candidate
fix — see below.

## What was measured

- `git grep -n "ZENOH_PICO_DIR/src\|zenoh-pico/src\|zenoh_pico_src"` over the
  tree (excluding the submodule, `third-party/`, prose): exactly one compiler of
  the vendored tree outside the two declared lanes — this script.
- `cargo build -p zpico-sys` compiles 131 vendored `.c`; the cmake lane's reader
  yields 133/134. This script's loop selects the same nine directories, so
  today the three agree. Nothing checks that they still will.

## Fix candidates, none chosen here

1. **Have the script read `zenoh-sources.txt`.** It is `file(STRINGS)`-shaped on
   purpose — a `while read kind group tree path` loop is a few lines — and it
   would answer the `always` group only, since bare-metal is neither Zephyr nor
   ISO-TP. Cheapest, and it fixes (1) alone — the three restated value sets
   (2), (3) and (4) stay.
2. **Delete it and make the readiness check a `fixtures.toml` row.** "Does the
   bare-metal zenoh-pico build?" is a compile-stage question, which is what the
   fixture manifest is for (CLAUDE.md: *"Does it compile?" intent → make it a
   build-step fixture and assert the artifact*). This removes all four copies
   rather than one, at the cost of the standalone `arm-none-eabi-gcc` path.
3. **Leave it and gate it**, which is what landed in the interim: the
   allowlist entry in `scripts/check-zenoh-lane-ownership.py`
   (`KNOWN_UNSHARED_COMPILES`) names this file with this issue id, so a FOURTH
   copy fails the gate while this one is a tracked, visible debt rather than a
   silence.

## Gate

`just check zenoh-lane-ownership` — check (7). A file that compiles the vendored
zenoh-pico tree must be a declared lane or carry a tracked issue id in the
allowlist; removing this entry without fixing the script turns the gate red,
which is the intended direction.
