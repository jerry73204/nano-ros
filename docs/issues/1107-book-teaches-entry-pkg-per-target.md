# A book page is what a new user copies, so a stale one propagates

## What the tree actually does

phase-383 W9/W10.a landed RFC-0065 D3/D4: **an image is a row, not a
directory.** `nros build` discovers the packages, reads the `[image.*]` table
in a bringup package's `system.toml`, and generates both the root build file
and the entry package from it.

The evidence is in the workspaces themselves. None of
`examples/workspaces/{c,cpp,rust,mixed}/` tracks a root build file:

```
$ git ls-files examples/workspaces/c | grep -E '^examples/workspaces/c/[^/]+$'
examples/workspaces/c/.colcon_workspace
examples/workspaces/c/.gitignore
examples/workspaces/c/README.md
```

`examples/workspaces/c/.gitignore` says why:

```gitignore
# phase-383 W10.a — the root manifest and root CMakeLists are GENERATED by
# `nros build` from the discovered packages plus the `[image.*]` table. They
# are build output like `build/` and `Cargo.lock`, and committing either would
# put a generated member list under review (RFC-0065 D3). The tracked marker
# that this directory IS a workspace root is `.colcon_workspace`.
/Cargo.toml
/CMakeLists.txt
```

The entry is generated the same way. RFC-0065 D4: *"the entry is derivable from
`(launch, args, board)` and is generated into `build/<coord>/`. A workspace
contains no entry packages."* `builder::entry::write` puts it at
`<ws>/build/<coordinate>/<image_id>_entry/`, and the board descriptor's
`entry.crate_root_extra` supplies the per-board shell, so the emitter carries no
per-board knowledge (`packages/cli/nros-cli-core/src/builder/entry.rs`).

`examples/workspaces/c/src/` therefore holds six node packages, one bringup
package, and **one** entry directory (`zephyr_entry`). The fourteen images that
workspace ships — `nros build` with no argument lists them — are fourteen rows
in `examples/workspaces/c/src/demo_bringup/system.toml`:

```toml
[image_defaults]
rmw = "zenoh"

[image.native]
board = "native"

[image.freertos]
board = "mps2-an385-freertos"

[image.freertos_posix]
board = "freertos-posix"
rmw = "cyclonedds"

[image.native_service_server]
board = "native"
launch = "service_server.launch.xml"

[image.zephyr]
board = "native_sim/native/64"
conf = ["prj-zenoh.conf"]
```

## The exception, and its reason

An entry package survives only where an external build system demands a real
application **directory**. That is Zephyr: a Zephyr app *is* the `app` target
`find_package(Zephyr)` creates, and it carries authored Kconfig
(`prj.conf`, `prj-<rmw>.conf`, `boards/`) that nothing derives — RFC-0065 D5,
*"west and ESP-IDF apps keep their own files because those are Kconfig
overlays — user intent, not derivable."*

The CLI states the rule itself. `nros new entry` (`cmd/new.rs:266`) refuses
every other platform:

```text
`nros new entry` currently scaffolds Zephyr entries only (got --platform X).
Every other platform builds through cargo or cmake, where the entry is
GENERATED from the image and needs no package of its own (RFC-0065 D3).
```

Migration is a **deletion**, not a cutover: `generate_entry`
(`cmd/build.rs:959`) keeps a hand-written entry when `src/<id>_entry/Cargo.toml`
or `CMakeLists.txt` exists, so removing the directory is what makes the next
build generate one.

## What the book claims instead

`book/src/getting-started/workspace-entry-pkg.md` — a page **titled** "Entry
packages", whose thesis is the retired model:

> You have one Entry pkg per deploy target. A workspace targeting both a native
> workstation and a bare-metal Cortex-M board has two Entry pkgs that reference
> the same Node pkgs; only the board and (optionally) the launch target differ.

It has a section headed `## One Entry pkg per board`, and mentions `[image.*]`
exactly once — as a place a `deploy` key "becomes the identifier … when you
later add a Bringup pkg".

The claim is repeated across the user track. Measured 2026-09-06:

| page | the claim |
| --- | --- |
| `getting-started/workspace-entry-pkg.md` | title, thesis, and a `## One Entry pkg per board` section |
| `getting-started/workspace-from-app-node.md` | "one Entry pkg per board or deploy target"; the ROS 2 command map maps `ros2 run` to "one Entry pkg per board" and says "there is no CLI build indirection" |
| `user-guide/component-and-entry-pkg.md` | "**One Entry pkg per board target** … Three Entry pkgs (`robot_entry_native`, `robot_entry_qemu_freertos`, `robot_entry_acme_threadx`)"; a workspace diagram with `src/robot_entry/` as a tracked member of a tracked root |
| `start-here/migration-guide.md` | the colcon→nano-ros row reads "one Entry pkg per deploy target" |
| `getting-started/workspace-mixed-language.md` | a layout with `src/native_entry/` (the mixed workspace has none), a `nano_ros_workspace(SUBDIRS …)` hand-written root, and two `nano_ros_entry(… MODEL "…/config/system_model.yaml")` blocks — a **tracked SystemModel**, which `check-no-tracked-models` bans (issue 0380) |
| `getting-started/anatomy.md` | "One entry per deployable image. A robot with a perception image and a control image is one workspace, two entry packages, one bringup" — the fifth page, outside the four first reported |

Three further pages carry dead run commands built on the same model:
`workspace-bringup.md` and `workspace-entry-pkg.md` both end on
`cargo run -p native_entry`, and `workspace-bringup.md` also calls the Bringup
pkg "optional: required only when two or more Entry packages share one
topology". `examples/workspaces/rust/src/native_entry/` has not existed since
phase-383 W9, and the bringup package is now where `[image.*]` lives, so it is
the one package a buildable workspace cannot do without.

## Why it is costly

A book page is what a new user follows, so a stale one does not decay quietly —
it propagates into every project scaffolded from it. This is not hypothetical:
a brand-new out-of-tree consumer was scaffolded with entry packages last week,
from these pages, before the author was corrected. The cost is paid twice, once
in the wrong tree and once in the migration off it.

It also compounds with the one shape that IS still required. A reader who
learns "an entry package per target" has no way to tell why Zephyr keeps one —
so when `nros build` refuses to derive a Zephyr application, the message reads
as a bug rather than as the boundary RFC-0065 D5 draws.

## Fix

`book/src/getting-started/workspace-entry-pkg.md` is retitled **Images** and
rewritten: `[image.*]` first, the generated entry second, the Zephyr exception
third with its reason. Its `#running-on-zephyr` anchor is kept —
`examples/workspaces/README.md` links to it. The path stays
`workspace-entry-pkg.md` so no inbound link breaks; renaming the file to
`workspace-images.md` is the tidier follow-up and needs that README in the same
commit, since `check-book-links` only scans `book/src/**` and would not catch
the break.

`workspace-from-app-node.md`, `component-and-entry-pkg.md`,
`migration-guide.md`, `workspace-mixed-language.md`, `workspace-bringup.md`,
`workspace-node-pkgs.md`, `workspace-cpp.md` and `anatomy.md` are corrected to
match.

## What is not fixed here

- **`getting-started/first-project.md` and the scaffolder templates → issue
  1108.** That page documents `nros new my_robot --workspace`, which still
  writes `src/robot_entry/`; four templates under `examples/templates/` still
  ship one, and two of them declare no `[image.*]` at all. The page is
  currently *accurate about what the scaffolder does*, so correcting it means
  correcting the templates, and the two have to land together. `anatomy.md`
  has the same dependency: its `src/robot_entry/` walkthrough is left in place
  and only its false generalisation ("two entry packages") is corrected here.
- **`examples/workspaces/{rust,c}/README.md`** still draw `native_entry/` in
  their tree diagrams and end on `cargo run -p native_entry`.
- **`examples/workspaces/rust/src/esp32_entry/`** is a hand-written entry that
  nothing structurally requires. It is not the Zephyr case: it carries no
  `CMakeLists.txt`, so `west_application_dir` could not resolve it as an
  application; `[image.esp32]` names no `entry =`; the esp32 driver is
  `Driver::IdfPy`, whose handoff runs `idf.py build` in the **bringup**
  directory (`native_handoff`, `cmd/build.rs:1939`); and
  `packages/boards/nros-board-esp32-qemu/nros-board.toml` already carries the
  exact two lines its `src/main.rs` hand-writes as
  `crate_root_extra = "use esp_backtrace as _;\nnros_board_esp32_qemu::esp_bootloader_esp_idf::esp_app_desc!();"`.
  Its one live consumer is the `workspace-rust-esp32` fixture row, which builds
  it directly with `cargo build -p esp32_entry --target
  riscv32imc-unknown-none-elf`. Deleting it means moving that row onto
  `nros build`, which is a build change, not a docs change.
